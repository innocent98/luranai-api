# SOP: WhatsApp channel, backend (demo slice)

**What shipped.** The Python/FastAPI side of the WhatsApp linked-device channel: a tenant enters a number, gets a pairing code, links it as a linked device, and the existing Luran AI/human pipeline answers their customers on WhatsApp. Text only, one tenant granted by hand. Branch `feature/whatsapp-channel-backend` → `develop` (PR linked from the hand-back). The sidecar (Node/Baileys) and the dashboard are separate tracks; this track ships a **fake sidecar** so everything is testable without Node.

Related: spike `docs/sop/whatsapp_pairing_spike.md`; plan `docs/superpowers/plans/2026-10-27-whatsapp-channel-backend.md` (with the agreed amendments at the top); FE guide `docs/fe-integration-guide-whatsapp-channel.md`; captures `docs/fe-integration-captures/whatsapp-channel/`.

## Why
Customers already write to businesses on WhatsApp; tenants asked for the AI to answer there without Meta approval. Option A (linked device through a Baileys sidecar) works today (spike), option B (Meta Cloud API) waits on Meta approval. Everything is behind one `Channel` abstraction so B is a new adapter, not a rewrite.

## How (decisions and trade-offs)
| Decision | Why / rejected alternative |
|---|---|
| `app/channels/` with a `ChannelAdapter` protocol; `linked_device` is an httpx client for the sidecar contract S; `cloud_api` is a stub that raises | B must slot in later. The sidecar's error vocabulary is mapped to typed errors (`CapacityExceeded`, `NotConnected`, `ReplyOnly`, `RateCapped`, `SidecarUnavailable`) so callers never parse HTTP |
| Contact / phone lookup keys are a **peppered HMAC** (`WHATSAPP_CONTACT_PEPPER`), not `hash_for_lookup` | `hash_for_lookup` is an unsalted SHA-256: a leaked column of phone hashes is brute-forceable. Missing pepper fails closed (503 `whatsapp_misconfigured`) |
| Phone and chat ref are `EncryptedString`; `Visitor.phone` is **never set** | Setting it would make the Visitor listener store an unsalted SHA-256 of the phone |
| The pairing code has **no column**, is not logged, and is not in any exception text | Returned once in the `201`/`200` body only |
| Webhook: raw body HMAC `t=<unix>,v1=<hex>` over `"t.rawbody"`, ±300 s, constant-time compare over both secrets (no short circuit), nothing derived from a signature is logged | Format copied from `spikes/whatsapp/src/sign.mjs`. Deliberately not the paystack handler, which logs a prefix of the expected signature. No IP rate limit (the HMAC is the authentication; a bad signature costs one HMAC); 256 KB cap |
| Tenant is resolved **only** from `session_key` server-side (webhook and job); unknown key → `200 {"status":"ignored"}`, nothing enqueued | The payload cannot name a tenant (an extra `tenant_id` is dropped by validation) |
| One arq job `process_whatsapp_event` for all three event types, job id = delivery id; per-chat Redis lock (`wa:chatlock:…`, retry in 2 s) | Replay-safe; two quick messages from one customer cannot race on session creation |
| Dedupe = `UNIQUE(connection_id, provider_message_id)` inserted in a savepoint; if the turn fails the row is removed so arq's retry is not swallowed | |
| AI reply is **enqueued** (`send_whatsapp_message`, job id `wa_send:<key>`), not sent inline | Own retry budget (5 tries, 5/15/45/120 s backoff), independent of the inbound job so a send failure never re-runs the LLM |
| Hard stop: sender refuses unless `connection.status == connected`; reply-only guard needs `last_inbound_at`; sidecar 409/503 are dropped, 429/5xx/timeouts retried | Never push on a half-linked session (it risks the number) |
| `source='whatsapp'` is passed through a `ContextVar` (`new_session_attribution`, like `voice_channel`) read where `chat.py` creates the session; `SourceMeta` gained `channel_connection_id`, `provider`; messages carry `meta.channel='whatsapp'` | Writing it by hand in two call sites would have missed the pipeline's own session creation; `coerce_source` would otherwise turn it into `unknown` |
| Session handling: reuse the chat's session while ACTIVE/ESCALATED/ABANDONED, new one once RESOLVED (the pipeline's own visitor lookup does the same); `chat.py` allows `entry_point='whatsapp'` for the visitor bootstrap | |
| Plan limit: `HTTPException(402)` from the pipeline → message stored when a conversation exists, **nothing sent** to the customer, tenant alert debounced to once per 6 h (`last_alert_at`; email is a TODO, logged only) | |
| Owner pause (O): `message.outbound_external` sets `human_until = now + WHATSAPP_OWNER_PAUSE_MINUTES` (120) and stores the text as `HUMAN_AGENT` with `meta {"source":"owner_phone"}` fanned out to agents with `to_customer=False` (True would echo it back to WhatsApp). While paused: customer messages are stored as USER messages and shown to agents through the pipeline's own `_fanout_customer_message`; AI not invoked; nothing auto-replied (non-text also silent). Each owner message extends the pause; it ends at `human_until` | Privacy choice: if the owner messages a contact that never wrote to the AI, **only the pause row is created** (no visitor, no conversation, no text), so the owner's personal chats on the same number are not copied into Luran |
| AI disabled per connection: same store-and-show-agents path as the pause | |
| Outbound hook: `maybe_forward` called once at the top of `connection_manager.fanout_event` (NOT `_deliver_event_local`, which re-fires on every worker). Forwards `agent_message`, `ticket_missed` (their `content`), `ticket_resolved` / `ticket_closed` (fixed text; `resolution_notes` is deliberately not sent). Inert when `WHATSAPP_ENABLED=false`, never raises | WS-only paths (typing, presence, `agent_left`) bypass `fanout_event`, so they are never forwarded |
| Capacity guard (C): `WHATSAPP_MAX_CONNECTIONS` (default 3) counts rows in `awaiting_pair/connecting/connected/reconnecting`, checked **before** the sidecar call under a Postgres advisory lock; the row is inserted before the sidecar call (so concurrent creates count) and deleted if the sidecar refuses. Sidecar `503 capacity_exceeded` maps to the same `503 capacity_exceeded` | 8 GB VPS shared with staging; RAM beyond one session is unmeasured |
| Abuse limits: each create / pairing code makes WhatsApp notify the target number's owner, so they are limited per tenant (10 per 10 min), per target number across tenants (5 per day, keyed by the peppered hash) and per connection (5 codes per 10 min), plus per IP on the pairing route. Pairing codes also require the grant to still be active, and re-pairing a `logged_out` connection re-runs the capacity guard | |
| arq job arguments carry chat text and Redis keeps them for 24 h, so the webhook event and the reply text are Fernet-sealed (`encrypt_field`) before `enqueue_job` and opened in the job | |
| Errors are the contract's flat `{code, message}` (a registered `WhatsAppError` handler), **not** FastAPI's `{"detail": …}`; auth failures still use `{"detail": "…"}` | Matches contract B literally; call it out to the FE |
| Automatic replies (AI, non-text fallback) carry `guard=True` and are re-checked at send time (owner pause, `ai_enabled`, grant); a reply queued before the owner took over is dropped (`dropped_paused`). Agent/ticket frames are not guarded | Found by the Opus review |
| Chat lock: random token with compare-and-delete, hashed chat ref in the key, up to 2 jobs per chat wait ~20 s in-job, others bounce with an arq retry (event job budget 30 tries) | Bounded worker-slot use by a spamming chat |
| `DELETE` fails closed: if the sidecar is unreachable the row is kept and the call is `502` | Deleting the row would orphan a live linked session nobody can unlink |

## Verification
- `tests/whatsapp/*` (fake sidecar, no Node, no LLM, no real number): signature valid/tamper/stale/future/wrong secret/rotation/missing/oversize; replay dedupe; unknown `session_key` dropped; payload cannot name a tenant; signature never in logs; consent version enforcement; capability + count gating; number in use across tenants; backend and sidecar capacity guard (and that the backend guard runs before any sidecar call); cross-tenant 404 on get/patch/delete/pairing-code; pairing code absent from every DB column and from loguru + stdlib logs; 402 path (nothing sent, debounced alert); owner pause (AI not invoked, pause extends, expires, no-transcript for strangers, replay-safe); AI-disabled path; `source='whatsapp'` and `meta.channel` persisted; session rotation on RESOLVED; sender hard stop for every non-connected status; reply-only; retry/backoff/give-up; fanout hook fires exactly once, not on remote-worker delivery, not for agent-only/WS-only/non-WhatsApp sessions; real REST agent endpoint → one enqueue; arq job wiring and idempotent enqueue against real Redis; migration upgrade/downgrade/upgrade on a scratch Postgres plus column/unique-constraint parity with the models.
- Live run against uvicorn + arq worker + Postgres 15 + Redis 7 with the **fake sidecar** (LLM stubbed): see the FE guide verification table and `docs/fe-integration-captures/whatsapp-channel/`.
- **Not verified:** the real Baileys sidecar; a real phone; the real LLM through this path; behaviour under WhatsApp bans; multi-worker concurrency of the chat lock beyond unit level.

## Operate / roll back
- Enable on staging: set the config names above, apply `alembic upgrade head`, then grant a tenant with `PUT /api/v1/platform/tenants/{id}/capabilities {"can_use_whatsapp": true, "max_whatsapp_numbers": N}`. The webhook is `POST {API}/api/v1/webhooks/whatsapp/linked`.
- Kill switch: `WHATSAPP_ENABLED=false` (webhook → 503, connection create/pairing → 403, inbound dropped, sender stops, fanout hook inert). Rows and conversations are untouched.
- Roll back code: revert the PR; the extra tables/columns are inert. Roll back schema: `alembic downgrade -1` (drops the three tables and the two capability columns; the `visitor_source` enum label stays).
- `WHATSAPP_CONTACT_PEPPER` must never change once connections exist: it keys `phone_hmac` and `contact_hmac`. Rotating it would break number uniqueness and re-split every chat.

## Follow-ups
- Per-tenant contact exclusion list (beta task T15) so the AI never answers personal contacts.
- Email/in-app alerts for plan-limit and disconnect (currently logged only).
- Unpaired `awaiting_pair` rows older than 30 min (from creation; new codes do not extend it) are discarded lazily (and logged out at the sidecar) when the next connection is created; there is no background sweeper, so they hold a capacity slot until then.
- Opus review leftovers (all LOW): `whatsapp_inbound_messages` is never pruned (add a 7-day purge cron); pause-only chat rows keep an encrypted `contact_ref` forever; consent version is not re-checked on re-pair after a version bump; tenant purge with the sidecar down deletes the rows anyway (no tombstone to retry the logout); a failure after `send_message` persisted makes arq re-run the turn (duplicate LLM turn).
- Status ordering: webhook `session.status` events are applied in arrival order; there is no per-event sequence guard.
- Pause/AI-off paths create conversations without the monthly-limit check.
- `from_ref` vs `to_ref` must be the same namespace for one chat (the owner-pause lookup keys on it): confirm with the real sidecar.
- Media in/out, structured-message renderer, tiered plan limits, option B adapter.
