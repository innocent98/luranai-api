# SOP: WhatsApp images (both ways), rating by reply, and the fallback fix

**What shipped.** Backend half of contract `2026-10-28-whatsapp-media-rating-contract.md` (sidecar half is another track). (1) A customer's WhatsApp **image** reaches the same pipeline as web-chat uploads and the AI reads it (vision); when the chat is paused, AI-off or human-owned the image is stored and shown to agents without the AI. (2) The fixed "I can only read text" reply no longer fires while a human owns the conversation. (3) An **agent's image** is sent to the customer's WhatsApp as a real image (the old text notice is gone). (4) The **rating request** is now delivered to WhatsApp and a bare `1`-`5` reply records the rating through the widget's own service. (5) When an agent takes over, the customer gets the join line `You're now chatting with <first name>.` (Adebayo's decision, 2026-10-28). Branch `feature/whatsapp-media-rating-backend` → `develop` (PR linked from the hand-back; not merged).

Related: `docs/sop/whatsapp_channel_backend.md` (text slice), `docs/sop/n4_agent_rating_backend.md` (rating requests), `docs/sop/chat_image_upload_backend.md` (image pipeline), `docs/sop/attachment_retention.md`; FE guide `docs/fe-integration-guide-whatsapp-channel.md` (section 8); captures `docs/fe-integration-captures/whatsapp-media-rating/`.

## Why
The 2026-10-28 live test proved text both ways but showed: customer images were stored only as a placeholder and the "text only" reply also fired while an agent was typing; agent images were replaced by a notice; and the rating request ("How was your chat with <agent>?") sat in the transcript but was **never delivered** to WhatsApp (`frame_text` forwarded only `agent_message`, `ticket_missed`, `ticket_resolved`, `ticket_closed`), with no way to answer it.

## How (decisions and trade-offs)
| Decision | Why / rejected alternative |
|---|---|
| `_process_image_upload` split into `screen_image_bytes` (size cap, real-format check, **fail-closed moderation**, no session needed) and `store_screened_image` (Cloudinary + `message_attachments`, retention from the model default); `process_image_bytes` = both. The web upload still calls the same code | WhatsApp must moderate **before** a conversation exists, so a blocked image from a new chat leaves nothing behind (no empty session). One function that did both would have forced creating the session first. Rejected: a second pipeline (drift), or a "skip moderation" flag |
| Inbound image order: tenant grant → dedupe row → **plan guard** → (derive silence) → fetch from sidecar → size + sha256 + mime check → `screen_image_bytes` → `_ensure_session` → `store_screened_image` → AI turn (`send_message` with `attachment_ids`, caption as text) or store-only | The plan/subscription/conversation-cap check runs **before** any byte is fetched, moderated (it costs a call) or stored |
| Store-only (no AI) when `human_until` is in the future, the connection has `ai_enabled=false`, or a human owns the conversation (`session.status == ESCALATED` or `session.agent_id` set): message + attachment linked, fanned out as `customer_message` through the existing `_fanout_customer_message` | Same rule the text path uses; `send_message` would also store-only for an escalated session but we decide earlier so the AI can never be invoked |
| Moderation block (or outage): store nothing, upload nothing, customer gets ONE fixed sentence (`IMAGE_BLOCKED_REPLY`), never the reason; silent when the chat is paused/AI-off/human-owned | Fail closed. "Store nothing" includes the caption |
| Unreadable image (sidecar 404/expired, wrong size or sha256, bad mime, not a real image, over the cap): placeholder stored for agents (`IMAGE_UNREADABLE_PLACEHOLDER`) + a fixed "couldn't open it, send again" / "too large" reply unless silent | The customer must not wonder; agents see that something arrived |
| Sidecar transport failure on the media fetch is **retried**: `SidecarUnavailable` → worker raises `arq.Retry(defer=15)`; the dedupe row is forgotten first. A storage (Cloudinary) failure raises and retries the same way. Any failure after the upload discards the still-unlinked attachment + the Cloudinary asset (best effort) | Media lives 10 minutes in the sidecar; a retry re-fetches. Idempotency: a redelivered event hits the dedupe ledger (`duplicate`) **before** any fetch/moderation/upload |
| Media bytes: streamed with a hard cap (`WHATSAPP_MEDIA_MAX_BYTES`, ≤ 10 MB) and a `Content-Length` pre-check; `media_id` must match `^[A-Za-z0-9_-]{1,128}$` (webhook schema AND adapter) before it is placed in the sidecar URL path; bytes are never logged (`MediaBlob.content` is `repr=False`) | Path-traversal / unbounded buffering |
| Fallback fix: `OTHER_KIND_REPLY` only for `kind:"other"` and only when `not (paused or ai off or human owns)`; otherwise the placeholder is stored and shown to agents, no reply. `skipped:"media_too_large"` gets a size hint instead of the text-only line. The reply text now says "text messages and images" | The old condition ignored an assigned agent / escalation |
| Outbound image: `maybe_forward` resolves the frame's attachment ids against **our DB** (same session, outbound, `IMAGE`, `LINKED`, https + host on `WHATSAPP_MEDIA_URL_HOSTS`, default `res.cloudinary.com`); only the attachment **id** travels in the arq job (`send_whatsapp_image`); the sender re-reads the row and re-validates at send time. The frame's own `url` is never used | A URL an agent could type or a frame could carry can never reach the sidecar. The sidecar enforces its own allowlist too (defence in depth) |
| Caption = the agent's text on the first image when ≤ 1024 chars; remaining images no caption; longer text goes as its own message (key `agent_message:<id>`) so nothing the agent wrote is lost; an image whose URL fails the checks still lets the text go out | |
| Image send errors: sidecar 400/413/415 → `MediaRejected` → `dropped_<code>`, **never retried**; 409/503/404 as for text; 429/5xx/timeout → same backoff (5/15/45/120 s, 5 tries). Idempotency key `agent_img:<attachment_id>` | |
| Rating forward: `frame_text` maps `rating_requested` → `How was your chat with <first name>? Reply with a number from 1 (poor) to 5 (great).` (no agent → the fallback prompt + the same suffix). The token in the frame is never used. The enqueued job carries `rating_request_id`; only when the send **actually succeeds** does the chat remember it (`whatsapp_chats.rating_request_id`, `rating_request_expires_at` = the request's expiry, 7 days) and only if the request belongs to that chat's tenant + session and is unfulfilled | A prompt that failed to send must not open a rating window; a stray digit must stay ordinary text |
| Rating reply (`_maybe_record_rating`, runs before the pause/AI logic): text must `fullmatch` `\s*([1-5])(\s*(/\s*5\|stars?\|⭐+))?\s*[.!]*\s*`; chat has an unexpired open request; plan not blocking; request and session belong to this tenant and `session.user_identifier == wa_<chat hmac>` (this chat's customer); then `ReviewService.rate_request_by_id` (new; row-locks the request by id + session + tenant, then the **same** `_fulfil_request` the widget token path now uses: unknown/foreign → invalid, fulfilled or already rated → `already_rated`, expired → expired). Success → clear the chat's request, one ack `Thanks! We've recorded your <n>/5.` (`rating_ack:<id>`, unguarded). Any refusal clears the chat's request and the text goes through the normal flow | No token is stored anywhere; nothing in the event names a request/session/tenant. Rejected: storing the plaintext token on the chat (a bearer secret at rest) and an HTTP self-call |
| Join line: `agent_joined` (emitted by `emit_agent_joined`, already `to_customer=True` through `fanout_event`, so no new hook) maps in `frame_text` to `You're now chatting with <first name>.` (no name → `a member of our team`). Key `agent_joined:<session>:<agent>`: a retried or repeated takeover by the same agent hits the same arq job id and sends once, a different agent sends again. Skipped when the chat is owner-paused at forward time. Unguarded (a human action), same retry and hard-stop rules. Limit: the same agent taking over again within the arq result retention (24 h) after another agent had the chat sends nothing | Every other system notice stays unforwarded |
| Rating window: a reply only counts if the request's session is the chat's CURRENT session (a digit typed in a new conversation is ordinary text); clearing is compare-and-clear on the request id so a late cleanup cannot wipe a newer prompt; no thank-you while the owner has paused the chat | Opus review findings 1, 4, 9 |
| Web-chat parity gates (Opus review finding 2): the tenant's `widget_allow_file_upload` switch is honoured (off → fixed `IMAGE_DISABLED_REPLY`, nothing fetched), and at most 10 inbound image attempts per chat per hour, counted in Redis (`RedisRateLimiter`, fail-open like the other limiters) BEFORE any fetch or moderation and whatever the outcome, so blocked images and chats without a session count too (over → noted for agents, no reply). Caught by the automated commit review | Each image costs a moderation call, an upload and a vision turn |
| A non-402 4xx from the pipeline after the upload is permanent (placeholder + polite reply, ledger kept) instead of a 30-try retry storm; the visitor row is created only after the plan guard and screening | Review findings 6, 7 |
| The ack failing to enqueue is swallowed (rating already committed) | Otherwise the arq retry would see a fulfilled request and send the "5" to the AI |

## What's involved
- **Changed:** `app/api/v1/endpoints/chat.py` (`screen_image_bytes`, `process_image_bytes`, `store_screened_image`), `app/services/whatsapp_inbound.py` (`_handle_image`, `_human_owns`, `_maybe_record_rating`, `_store_image_without_ai`, constants), `whatsapp_outbound.py` (`_preflight`, `send_image`, `media_url_allowed`, `outbound_image_url`, rating memory), `whatsapp_dispatch.py`, `whatsapp_enqueue.py` (`enqueue_send_image`, `rating_request_id`), `app/workers/whatsapp.py` (`send_whatsapp_image`, `Retry` on `SidecarUnavailable`), `app/workers/document_processor.py` (registers the job, `max_tries=5`), `app/channels/{base,linked_device}.py` (`fetch_media`, image `send`, `MediaNotFound/TooLarge/Rejected`), `app/schemas/whatsapp.py` (`kind` gains `image`, `media`, `skipped`; an image event without `media` still validates and is handled as unreadable, so the two PRs deploy in either order; sidecar `502 image_fetch_failed` on an image send is transient and retried), `app/services/review_service.py`, `app/db/models/whatsapp.py`, `app/core/config.py` (`WHATSAPP_MEDIA_URL_HOSTS`, `WHATSAPP_MEDIA_MAX_BYTES`).
- **Migration `wa20ratingreply`** (down `ent10entitlements`, single head): `SET LOCAL lock_timeout='5s'`; adds `whatsapp_chats.rating_request_id` (FK `rating_requests` ON DELETE SET NULL) and `rating_request_expires_at`. Upgrade → downgrade -1 → upgrade proven on scratch Postgres 15.
- **Tests:** `tests/whatsapp/test_media_inbound.py` (34), `test_media_outbound.py` (34), `test_rating.py` (49), additions to `test_webhook.py`; `tests/fakes/fake_sidecar.py` gained the media endpoint, image send (with the real sidecar's host allowlist) and `/_fake/media`; `tests/fakes/live_stub.py` stubs moderation and Cloudinary; capture rig `tests/fakes/live_capture_media.py`.

- `ruff check app/` clean, `black --check app/` clean (ruff 0.8.6, black 24.10.0, Python 3.11 poetry env), full suite `pytest tests/` **2375 passed, 33 skipped** (after the review fixes and the join line; `tests/whatsapp` + `tests/rating` re-run after the last schema tweak: 366 passed) on Postgres 15 + Redis 7, SQLite regression pair 14 passed, `alembic upgrade head` / `downgrade -1` on scratch Postgres, single head.
- Live local run (API + arq worker + fake sidecar, LLM/moderation/Cloudinary stubbed; captures in `docs/fe-integration-captures/whatsapp-media-rating/`): image+caption → vision call saw 1 image → AI reply delivered; flagged image → fixed sentence, nothing stored; corrupt sha256 → "couldn't open"; AI-off image stored with attachment, no send; voice note while escalated → stored, no send; voice note with nobody owning → fixed reply; agent image+caption → sidecar received `{image:{url,caption}}`; rating request → prompt delivered → "5" → thanks → rating listed against the agent and ticket → second answer treated as ordinary text; agent takeover → `You're now chatting with Alpha.` delivered.
- Logs of that run were grepped for the caption, agent text, rating copy and both phone numbers: no hits.
- **NOT verified:** the real Baileys sidecar (its media endpoint, image send, `kind:"image"` events, same-ref behaviour for images), real OpenAI moderation, real Cloudinary upload/delivery, the real model's vision answer, a real phone. Needs the live staging test.

## Operate / roll back
- Config: `WHATSAPP_MEDIA_URL_HOSTS` (default `res.cloudinary.com`; keep it equal to the sidecar's `MEDIA_URL_ALLOWLIST`), `WHATSAPP_MEDIA_MAX_BYTES` (default 10 MiB). New arq function `send_whatsapp_image`: deploy the API and the **worker** together (an old worker would not know the job).
- Roll back: revert the PR, `alembic downgrade -1` (drops the two nullable columns; nothing else depends on them). Existing in-flight `send_whatsapp_message` jobs with the old 5-argument shape still run (`rating_request_id` is optional).

## Decisions worth knowing
- `widget_allow_file_upload` IS applied to WhatsApp images (review finding): a tenant that turned uploads off gets no images on WhatsApp either.
- The monthly conversation cap is checked up front for images; unlike text it is not re-checked by `send_message` after the upload (the upfront check is the same count).

## Opus security review
Verdict NO BLOCKERS (nothing crosses tenants, no unmoderated image is stored, the rating token never reaches Redis/DB/logs). Fixed: findings 1, 2, 4, 6, 7, 9. Left as follow-ups: (3) agent text travels only as the first image's caption, so it is lost if that one image send is dropped; (5) a storage failure after `_ensure_session` leaves an empty session; (8) an enqueue failure after the turn committed retries and double-stores; (10) the 120 s chat lock can expire during a slow fetch + moderation + vision turn; (11) a moderation outage looks like a flag to the customer and is invisible to agents on silent chats.
