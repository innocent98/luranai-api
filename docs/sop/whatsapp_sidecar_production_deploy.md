# SOP: WhatsApp sidecar on PRODUCTION (pipeline wiring, dark), 2026-10-29

## What shipped
The pipeline, compose and monitoring wiring that deploys the WhatsApp sidecar (`whatsapp-sidecar/`) to the **production** stack through the existing `production-deploy` CD job, **only when its secrets exist**; with no sidecar names in the encrypted production env nothing changes. It never turns WhatsApp on: `WHATSAPP_ENABLED` stays whatever the env says (the secrets generator writes `false`). Branch `feature/sidecar-production-deploy` -> `develop` (PR link in the hand-back). Staging pattern it mirrors: `docs/sop/whatsapp_sidecar_staging_deploy.md`. Nothing here has run on the VPS.

> **Update 2026-10-30:** the Redis and network layout described below (shared Redis DB 1, `luran_default`) is **superseded** by `docs/sop/whatsapp_sidecar_redis_isolation.md`: the sidecar now has its own authenticated Redis on an internal network and no longer shares a network with the production Redis, Qdrant or pgbouncer. Where this SOP says "shared", read that SOP. The new required env name is `WHATSAPP_SIDECAR_REDIS_PASSWORD` (sidecar-only).

## Why
`docs/deployment/prod-release-plan-2026-10.md` section 6: WhatsApp for real tenants needs a production sidecar job mirroring staging, a prod guard, a prod DB role, generated and backed-up secrets, and a memory budget on the shared 7.8 GiB host. The code ships dark in prod; this is the blocker for enabling it.

## How
| Area | Decision |
|---|---|
| Gate | `scripts/prepare_production_whatsapp_env.sh`, a new step in `production-deploy` between "Decrypt production .env" and "Copy files to production stack directory" (it must run before `.env` is shipped). **No sidecar names in the env -> the script touches nothing** (env bytes and mode unchanged) and logs `SKIPPED - no WhatsApp sidecar names`. Names present -> required ones present and well-formed (same rules as staging: token/secret >= 32 chars, master key hex >= 64, DB password `[A-Za-z0-9]{24,}`) -> `sidecar_enabled=true` and `backend_mode=enabled|disabled` (from `WHATSAPP_ENABLED`); else skipped with NAMES only. Sidecar-only secrets are stripped from `.env` into `.env.sidecar` whether or not the gate passes |
| Production guard (mirror of staging's project check) | Runner: if the env names `COMPOSE_PROJECT_NAME` it must be `luran`; if it sets `ENVIRONMENT` it must be `production` (a staging env pasted into the prod file is refused). Server, in the deploy step: `.env` project name (if any) must be `luran`; the running **`luran_api` container must carry compose label `project=luran` and its `working_dir` must be this directory**; compose is always called with `-p luran`. So the sidecar can only join `luran_default`, never staging's network |
| Gate step is fail-closed | Unlike the optional steps it is NOT `continue-on-error`: if it cannot run, the secrets would otherwise be shipped inside the api env, so the deploy stops. Its no-names path is a no-op, so this only bites when the script itself is broken |
| Image | Promoted, not rebuilt, like the API: `docker pull ghcr.io/<repo>-whatsapp-sidecar:develop` (built by `docker.yml` on every develop push), `docker save` + scp, `docker load` on the VPS (no registry login there). The log prints the digest and the develop commit label. Like the API, **the moving `:develop` tag means whatever develop built last ships**. Every prod deploy therefore recreates the sidecar once if a newer image exists (about 20 s, sessions restore from Postgres without re-pairing; WhatsApp queues messages for linked devices) |
| Deploy | Copy (image, both compose files, `.env.sidecar`, DB-init SQL, smoke, snapshot script); ssh: `chmod 600 .env .env.sidecar` (the earlier prod step leaves `.env` 644; staging does the same tighten), guards, `docker load`, `dc config -q`, `whatsapp-db-init` (idempotent), `up -d --no-deps whatsapp-sidecar`, health loop (20 x 5 s; unhealthy -> stop, no restart loop), print effective limits and the sidecar Redis's memory lines, smoke (21 `PASS` + 1 `SKIP` with the isolation checks), prune to the 3 newest sidecar images. Steps are `continue-on-error`; a status step warns |
| Compose | Three files: `docker-compose.prod.yml` + `docker-compose.whatsapp.yml` (staging's, **effective staging config byte-identical before/after**, only its header comment changed) + **new** `docker-compose.whatsapp.production.yml` (literal `container_name: luran_whatsapp_sidecar`, memory/session defaults; the image is tagged `luran-whatsapp-sidecar-prod:<sha>`, a repo name of its own, because staging prunes `luran-whatsapp-sidecar` to the 3 newest on every develop deploy on the same host). Hardening is inherited: read-only rootfs, caps dropped, no-new-privileges, no swap, `oom_score_adj 500`, no published port, 30 MiB log cap |
| DB | Same `scripts/whatsapp_sidecar_db_init.sql` as staging, run against the prod DB as the stack superuser: role `whatsapp_sidecar` (NOSUPERUSER, no CREATEDB/ROLE, `CONNECTION LIMIT 8`), **no CREATE on the database**, schema pre-created and owned by the role, no grants on application tables. Direct to `db:5432`, **bypassing pgbouncer** (session advisory lock; pgbouncer does not know the role). **New: the init SQL now asserts least privilege itself and aborts before the sidecar starts** if the role has CREATE on the database or on any schema but its own, or any table/sequence privilege outside its schema (catches a legacy ACL such as a volume upgraded from PostgreSQL <= 14, or a grant to PUBLIC; names only in the error). The smoke also checks CREATE, as a second look after start. A smoke failure only warns (it does not stop a sidecar that may hold live sessions) |
| Redis | **Superseded 2026-10-30 (`whatsapp_sidecar_redis_isolation.md`).** Originally the sidecar used logical DB 1 of the shared production Redis. It now uses its own `luran_whatsapp_redis` (ACL user, password only in `.env.sidecar`, `noeviction`, `maxmemory 8mb`, `save 60 1`, 32m) on the internal network `luran_wa_redis`, and sits with `luran_api`, `luran_worker` and `luran_db` on `luran_wa_backend` instead of `luran_default`. Fail-closed behaviour in the sidecar (offline queue off, 3 s timeout, lease heartbeat, `SET NX` re-take) is unchanged |
| Secrets | Generator `scripts/generate_whatsapp_production_secrets.sh` (prints nothing, 0600 file, git-ignored, refuses to overwrite, fresh values, `WHATSAPP_ENABLED=false`, `WHATSAPP_MAX_CONNECTIONS=3`). Master key and DB password live only in `.env.sidecar` (0600 on the server); token and webhook secret are shared with the backend by design |
| Smoke | `SMOKE_BACKEND=disabled` mode (what CD passes while `WHATSAPP_ENABLED` is off): the disabled backend answers 503 before checking signatures, so the webhook check is "reachable and reports disabled" and the bad-signature check is reported **SKIP, not PASS**. Default mode (staging, unchanged) and `SMOKE_BACKEND=enabled` are strict. A wrong mode FAILS |

### How the CD trigger model affects this (read before merging or promoting)
- `workflow_run` workflows run from the **default branch (`main`)**: merging this PR to `develop` changes **nothing** for staging's automatic deploys or production until `develop` is promoted to `main`. (Staging got its sidecar by manual dispatch from a branch; same applies here.)
- A push to `main` runs `production-deploy` straight from the pushed commit: **no staging gate, no CI re-run**. So the promotion that carries this file is itself the first run of the new steps. With no sidecar names in `.env.production.enc` (the state after this PR) that run is the skip path: the gate step logs `SKIPPED`, `.env` is shipped byte-identical, no other new step runs. The only behaviour change on that promotion is one extra no-op step.
- `workflow_dispatch` with `environment=production` redeploys the **whole** prod stack from the chosen ref (migrations, `up -d`, image `:develop`). It is the only way to deploy the sidecar without a `main` push, and it is not sidecar-only.
- **Ordering trap:** a `.env.production.enc` containing `WHATSAPP_AUTH_MASTER_KEY` / `WHATSAPP_SIDECAR_DB_PASSWORD` must never be deployed by a workflow file that lacks the strip step (an older `main` cd.yml would put the master key into the api and worker env). The encrypted env therefore must not reach `main` before this PR does. The normal path (PR for the env change to `develop`, then promote) respects this; a hotfix straight to `main` or a dispatch from an old ref would not.

## Sizing and the memory budget
**Measured** (staging, 2 linked test numbers, real text and images, 21 h; limit 384 MiB, 0.5 CPU): container memory 79.8 MiB at start, 85.2 after 65 min, 88.9 after 21 h, peak 97.3 MiB (image burst); process RSS 135-144 MB; 0 restarts, 0 OOM kills; 13 automatic socket reconnects in 17 h. Memory reads by `docker stats` exclude page cache; the snapshot script's `memory.current` includes it (a fresh rehearsal container read 128 MiB with `anon` 62 MiB), so trend `anon` and `rss_mb`, not `memory.current`.

| Setting | Production value | Basis | Status |
|---|---|---|---|
| `WHATSAPP_RSS_REFUSE_MB` | **216** | peak process RSS 144 MiB x 1.5 (`/health` `rss_mb` divides by 1048576, so these are MiB) | policy applied to a **measured** peak. Must exceed normal RSS or restores are refused: it is 72 MiB above the 2-session peak |
| `WHATSAPP_MAX_SESSIONS` | **3** | measured 2 sessions x 1.5 | **EXTRAPOLATED**: only 2 sessions were ever exercised. The third number is itself the first measurement (watch the snapshot log). Crude RSS slope from idle (95-101 MiB) to 2 sessions (135-144 MiB) is 17-24 MiB per session, two data points, not a fit |
| `WHATSAPP_SIDECAR_MEM_LIMIT` | **384m**, no swap | RSS refuse 216 MiB + 32 MiB `/tmp` tmpfs + about 48 MiB for the HEALTHCHECK `node` process (estimate from the soak SOP) + about 50 MiB for the deploy smoke's `node` process = 346, rounded up to a 64 MiB step | derived; equals the limit staging ran the whole measurement on. The pure cgroup rule (measured peak 97.3 MiB x 1.5 = 146 -> 192 MiB) would sit below the refuse guard's worst case (the guard gates only new sessions and restores, not growth), so the OOM killer could pre-empt it |
| API `WHATSAPP_MAX_CONNECTIONS` | **3** (also the code default) | must not exceed the sidecar cap | prep script warns if it does |
| CPU / pids / oom_score_adj | 0.5 / 256 / 500 | unchanged from the measured configuration | measured |

**Staging values are not production values.** The staging sidecar runs `WHATSAPP_RSS_REFUSE_MB` **300**, a **384 MiB** limit and **2** sessions (`docker-compose.whatsapp.yml` defaults); those are staging-only guards, not a sizing. Production overrides them in `docker-compose.whatsapp.production.yml`: **216 / 384m / 3**. Only the limit happens to match staging's.

**3 sessions is a hard launch ceiling.** Production starts at 3 numbers platform-wide, enforced twice (sidecar `MAX_SESSIONS` 3 returns 503 `capacity_exceeded`; backend `WHATSAPP_MAX_CONNECTIONS` 3 returns the plan-limit message). It stays 3 until the Phase 2 soak (`docs/sop/whatsapp_sidecar_soak.md`) has measured 4-6+ real sessions with load, a 24 h hold and a restart.

**To raise the ceiling after Phase 2** (one env change plus a restart, three values that move together): in `.env.production.enc` set `WHATSAPP_MAX_SESSIONS=N` (sidecar), `WHATSAPP_MAX_CONNECTIONS=N` (backend; the prep script warns if it exceeds the sidecar's) and, from the soak report's recommendation, `WHATSAPP_RSS_REFUSE_MB` and `WHATSAPP_SIDECAR_MEM_LIMIT`; commit, promote, and run a production deploy (the deploy recreates the sidecar with the new values and restarts the api). Raising only the session counts without the RSS guard and memory limit risks refusals or OOM kills, because at N sessions the RSS guard (216 MiB today) trips first. Hotfix without a deploy: on the VPS run the compose command from the override file's header with `WHATSAPP_MAX_SESSIONS=N WHATSAPP_RSS_REFUSE_MB=.. WHATSAPP_SIDECAR_MEM_LIMIT=..` in front, and restart the api with `WHATSAPP_MAX_CONNECTIONS=N` in its env; the next deploy resets both to whatever the encrypted env says, so put the same values there.

**Capacity statement (do not promise more):** production admits **3 WhatsApp numbers platform-wide**, 2 of them proven. The fourth and later need the N-session soak (`docs/sop/whatsapp_sidecar_soak.md`, not yet run) and a deliberate raise of both caps. Tenants beyond the cap get the sidecar's 503 `capacity_exceeded` / the backend's plan message.

Shared-host budget (MiB; limits and usage from the 2026-10-28 host reading; staging sidecar at its 21 h figure):

| Stack | Sum of limits | Observed use |
|---|---|---|
| Production api 1200, worker 2000, qdrant 1024, redis 384, db 1400, pgbouncer 128 | 6136 | 1432 (api 1000, mostly reclaimable slab; its `anon` is 378) |
| Staging api 768, worker 1024, qdrant 192, redis 64, db 384, pgbouncer 48, sidecar 384 | 2864 | 722 |
| **Before this change** | **9000 (8.8 GiB)** | **2155 (2.1 GiB)** |
| Production sidecar | 384 | expected 89-97 (2 sessions, measured), about 110 at 3 sessions (extrapolated) |
| **After** | **9384 (9.2 GiB)** | **about 2.25 GiB expected; 2.48 GiB if the sidecar sat at its limit** |

Limits already exceed the host's 7.8 GiB (7987 MiB) and this adds 384; that is safe only while real use stays near 2-2.5 GiB. The sidecar has the highest OOM-kill priority, so under host pressure it dies first and production is spared. Re-check when the host passes 5 GiB in use.

## Monitoring (`scripts/whatsapp_sidecar_snapshot.sh`)
One CSV line per run: `utc,mem_current_b,anon_b,sessions,rss_mb,socket_closed_5m,err`, appended to `logs/whatsapp_sidecar_snapshot.csv` next to the app logs (override `WA_SNAPSHOT_LOG`). One `docker exec` runs bash and cat inside the container, so the bearer token is expanded by the container's shell and never reaches the script, argv, the log or cron mail. The in-container read has a 10 s timeout (a hung sidecar cannot pile up stuck processes inside the 384m cgroup) and the host-side docker calls 25 s. Rotation at 256 KiB, 2 files kept (under 0.8 MB on disk); a line is about 60 bytes, so 288 lines/day is about 0.5 MB/month. A run took 0.12 s wall in the rehearsal. Exit 0 whenever a line was written (the `err` column carries `container_down`, `exec_failed`, `health_<code>`, `cgroup_unreadable`, `health_unparsable`); exit 1 only if the log cannot be written.

Install on the VPS as the deploy user (no sudo; CD copies the script with the sidecar files, and the CD cron install only removes lines matching `backup_cron.sh` / `backup_db.sh`, verified on a simulated crontab, so this line survives deploys):
```bash
chmod +x /opt/luran/scripts/whatsapp_sidecar_snapshot.sh
( crontab -l 2>/dev/null | grep -v -F whatsapp_sidecar_snapshot.sh; echo '*/5 * * * * /opt/luran/scripts/whatsapp_sidecar_snapshot.sh >/dev/null' ) | crontab -
```
Run it once by hand first and look at `tail -2 /opt/luran/logs/whatsapp_sidecar_snapshot.csv`. If the script says it cannot write, the `logs/` directory is root-owned (created by Docker's bind mount): `sudo chown` it once or set `WA_SNAPSHOT_LOG` to a path under your home. Read it later with `column -s, -t < logs/whatsapp_sidecar_snapshot.csv | tail -40`. Worry when: `anon_b` climbs steadily over days, `rss_mb` approaches 216, `err` is non-empty for more than a couple of lines, or `socket_closed_5m` is well above the staging rate (about 13 per 17 h; a burst of many per window means a reconnect storm).

## Rulings made (cost if wrong)
- **RESOLVED 2026-10-30 (`whatsapp_sidecar_redis_isolation.md`).** Original ruling, kept for the record: the sidecar shared the prod Redis (logical DB 1) and the default network with unauthenticated Redis and Qdrant, as the brief said (reuse staging's decisions). The staging review (`docs/superpowers/plans/2026-10-28-sidecar-staging-deploy.md` section 4) said not to copy this layout to production before a dedicated Redis on a private network plus ACLs. Isolating the sidecar needs `docker-compose.prod.yml` changes that restart prod services, so it is deliberately not in this PR. *If wrong:* a compromised sidecar (it parses untrusted WhatsApp traffic) could write the arq queue or read/overwrite Qdrant. Mitigations in place: dark by default, 3-session cap, least-privilege DB role, no published port. **Decide before `WHATSAPP_ENABLED` is flipped for real tenants.**
- **`MEM_LIMIT 384m` instead of the pure cgroup rule's 192m** (and not the first-draft 320m: the Opus review pointed out the refuse threshold is MiB, so the worst case plus the deploy smoke is 346 MiB). *If wrong (too large):* up to 192 MiB of unused headroom on a host with 6 GiB free, with top OOM priority. *If 192 were used and wrong:* the OOM killer could fire under an image burst before the RSS guard, dropping all numbers for about 20 s.
- **`MAX_SESSIONS 3` is one beyond anything measured.** *If wrong:* the third number runs on extrapolation; mitigated by the 216 MiB RSS guard, the 384m limit with top OOM priority, and the snapshot log.
- **Gate step fail-closed (not `continue-on-error`).** *If wrong:* a bug in the script blocks a prod deploy (visible, nothing shipped); the alternative could silently ship the master key in the api env.
- **`.env` is tightened to 600 only by the sidecar step** (the existing prod step is byte-unchanged and leaves it 644 until then; `.env.sidecar` is also 644 for the seconds between scp and the ssh step, because the scp container cannot read a 600 file). *If wrong:* a local user on the VPS could read the shared token and webhook secret in that window (not the master key's absence: the master key is only in `.env.sidecar`, same window). Backup cron runs as the same user as the owner of the file, as on staging.
- **Sidecar redeploys on every prod deploy** (new image ID each develop build). *If wrong:* a brief reconnect per promotion; promotions are infrequent and the API restarts then anyway.

## Decommission
Removing the names from the env does **not** stop a running sidecar and does not delete the server's `.env.sidecar` (which holds the master key). To retire it: set `WHATSAPP_ENABLED=false`, `docker stop luran_whatsapp_sidecar && docker rm luran_whatsapp_sidecar`, `shred -u /opt/luran/.env.sidecar` (or `rm`), remove the snapshot cron line, then `DROP SCHEMA whatsapp_sidecar CASCADE; DROP ROLE whatsapp_sidecar;` if the data should go.

## Launch ceiling and the flip (2026-10-30, owner decision)
The sizing table above (3 sessions, RSS refuse 216, limit 384m) is what the sidecar shipped with. For the public flip the owner chose a **launch ceiling of 10** (not 3) so real businesses can be onboarded; this is an env-only change (PR #187, `.env.production.enc`, names only):

| Setting | Was | Flip value | Basis |
|---|---|---|---|
| `WHATSAPP_ENABLED` | false | **true** | public flip |
| `WHATSAPP_MAX_CONNECTIONS` / `WHATSAPP_MAX_SESSIONS` | 3 | **10** | owner choice |
| `WHATSAPP_RSS_REFUSE_MB` | 216 | **512** | pessimistic ~340 MB process RSS at 10 numbers x 1.5 |
| `WHATSAPP_SIDECAR_MEM_LIMIT` | 384m | **768m** | formula gives ~704m (512 + 32 /tmp + 48 healthcheck + 50 smoke, rounded to 64); one step up because it is an extrapolation |
| `WHATSAPP_SIDECAR_CPUS` | 0.5 | **1** | reconnect storm after a restart |
| `WHATSAPP_SIDECAR_REDIS_PASSWORD` | absent | **added** | needed by the isolated Redis (`whatsapp_sidecar_redis_isolation.md`) |

**Status: ESTIMATED, not measured.** Only 2 numbers were ever soaked (peak container 97.3 MiB, process RSS 135-144 MB; crude 17-24 MB per number from two points). The wall (768m) is deliberately far from the expected use so a wrong estimate shows up as a refused new number (RSS guard) and not as a kill that drops every number. Mitigations: onboard a few businesses at a time, read the snapshot CSV / `docker stats` at about 3, 6 and 10 numbers, capacity email near 8, rollback `WHATSAPP_ENABLED=false`. WhatsApp is plan-driven default-on (no per-tenant grant), so anyone with a live trial or plan can connect until the ceiling: the 10 slots are first come, platform-wide. Staging keeps its own ceiling of 2.
