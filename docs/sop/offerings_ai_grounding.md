# Offerings catalog: AI grounding path (stream S2)

**What shipped:** the AI reads the tenant's catalog live from Postgres before every model call, injects an authoritative block, checks the reply in code (price guard, one regeneration, code fallback), writes `meta.offerings` cards, turns a chosen cart into a lead with wanted items, a catalog quote and an owner alert, and takes the lead `source` from the channel. Branch `feature/offerings-ai-grounding`, **draft PR #197** (stacked on S1's #195; the lead retargets it to `develop` after S1 merges). No migration (S1's `of10offerings` owns the tables). Nothing merged, nothing deployed.

Spec: `docs/superpowers/specs/2026-10-30-offerings-catalog-design.md` sections 7 and 8. Plan: `docs/superpowers/plans/2026-10-30-offerings-catalog-build-plan.md` section 3 (S2 T1-T8). FE guide part 2: `docs/fe-integration-guide-offerings-part2.md`; captures `docs/fe-integration-captures/offerings-ai/`.

## Why

A price or a stock level read from an embedded KB chunk can be days old, and a wrong price the AI quoted on WhatsApp is a money dispute the business must honour. The chat path makes one model call, so the lookup is done by the backend **before** it, and the reply is checked by code **after** it. Prices and totals are never trusted model output.

## How (decisions and what was rejected)

| Decision | Reason / rejected alternative |
|---|---|
| Lookup is Postgres lexical search scored in SQL (name x3, keywords x3, category x2, description x1, word-prefix), no vector index | Spec 7.2. A semantic index returning ids only is the v1.5 option if the miss log shows poor recall |
| Block capped at **1,000 tokens** with the project token counter; lowest-ranked items are dropped first, and only items that survive are "injected" (the guard's allowed set) | Cost must not grow with the catalog (test: 5,000 items) |
| Tenants with no active items (or catalog switched off) get a **byte-identical** prompt and cost **one indexed `LIMIT 1` query per turn** (no count, no savepoint) | Pinned by `tests/offerings_ai/test_prompt_unchanged.py` against `golden_prompts.json` captured from S1's head before any change (plain and sales mode, prompt, system message, response schema) |
| The strict schema is not edited: `SALES_RESPONSE_SCHEMA_OFFERINGS` is a deep copy plus `catalog_refs`, `cart`, `offered_price` in `signals` | Plan risk 1 checked first: the only consumers are `parse_sales_output`, `signals.get(...)` in `chat.py` and `score_lead`, all tolerant. No `maxItems` (not portable in strict mode); caps are enforced in `parse_catalog_signals` |
| **Structural guard: price tokens (review pass 3).** The block shows each item's price as `[[price:#N]]`, never an amount, and a "Price order, lowest first" line for comparisons. The model writes the token; **after** the guard, `finalize_reply` (`app/offerings/tokens.py`) resolves it to that exact item's live `price_text` (web, WhatsApp and voice all go through `send_message`; a reply with an unresolvable token gets the fallback; token-like text is stripped when no block was injected). `guard.py` then enforces: any literal amount outside a token, outside a code-written line and outside a KB sentence that names **no** catalog item (checked against **all** the tenant's active item names, not only the injected ones) is a violation; an unknown, foreign or malformed token is a violation (`unknown_token`, `bad_token`, `token_mismatch`, with carry-forward for follow-on sentences); plus bundle / same-price claims, anchored discount wording, and agreement wording while an offer is in play. The older amount-pattern checks stay as a backstop | The v1 guard chased wording patterns and three review passes kept finding new ones (swapped prices, carry-forward, bundles, variants, KB laundering). Tokens remove the swapped-price and typed-amount classes by construction. Lead decision 2026-10-31, reversing the earlier recommendation not to do it |
| One regeneration **of the same call type**, then a reply built from the rows; both calls' tokens count toward the turn | Spec 7.5. A fallback also offers a human through the existing escalation consent flow |
| A catalog hit or browse counts as grounded and skips the "short reply, offer escalation" quality heuristic | Otherwise "The black sneaker is ₦12,000." got a team-offer appended. **Deviation from the spec text (7.1 step 7 only named `has_no_retrieval`)** |
| The cart in `signals.cart` is the **complete current selection**; a later non-empty cart replaces the lead's interests, an empty cart never clears them | One rule the model can follow every turn; removal works when other items remain |
| **[call]** No catalog quote while a customer's price offer is pending; no quote for a cart containing a `from` or `on_request` line; a quote identical to the lead's latest one is not created again | A quote at the listed price beside a counter-offer would mislead; a changed cart makes a new quote |
| D1 handover: an offer below the listed price on a **negotiable** item (or a repeated offer on any item) offers a human through the escalation consent flow; offers at or above the listed price do not | Spec 7.6 rule 3 |
| Not-found log: the term is taken from the phrase after an ask cue ("do you sell X", "I want X"), after removing emails, URLs and number runs; chit-chat records nothing | Privacy: a normalised term only, no session, customer or raw text |
| Owner alert `OFFERING_REQUEST` fires once per lead, after the lead is enriched so it carries the name | The score cannot reach 86 for a WhatsApp buyer; the alert does not depend on it |
| **Bargaining turns are code-only (S-B).** `offer_turn.py`: when the customer's latest message holds a figure below a price in play, a percentage, or bargaining words, or the model returned `offered_price`, the model's text is dropped (no guard, no quality check) and the reply is built from fixed sentences: the firm price (`price_text`, so a `from` item reads `from ₦5,000`), "open to offers" / "noted your offer" plus the handover line for negotiable items, or "a team member will confirm". Offers at or above the list are ignored; whenever the confirm line is written the conversation is handed over (`AUTO_ESCALATE`; on voice a consent step, `OFFER_ESCALATION`, never a silent handover) | An LLM never gets to word a negotiation. Side effect: the model can no longer answer a haggle with a clever refusal; the fixed sentences are plain on purpose |
| **Other pass-3 fixes.** (a) a failed catalog-gate query now fails **closed** (strict reply, session rolled back) instead of silently ungrounded; (b) shown-items memory only feeds short or anaphoric follow-ups, not every turn; (c) the quote is derived from the stored rows under the lead row lock (`stored_lines`), so a partial cart can never quote a smaller selection; (d) the plan-tier quote is withheld whenever the catalog is active and the turn touched it; (e) voice speaks the code lines (no silent tool call) and a token is never spoken; variants (Pro/Large prefixes), `from` items, units (never money), "free/cheaper/drop off" only when anchored, bare digits only with price context, KB-verbatim sentences allowed | Review pass 3 plausibles and false-block fixes. Block rates: the fashion n40 set 0 unexpected blocks (2 expected blocks stay blocked, ≤3% target), the 40-reply clinic/lawyer set 0 blocked |
| **T6 review (Opus, read-only) fixes.** A total or line past the 32-bit quote column (2,147,483,647) makes **no quote**, adds a code sentence and hands over (no migration: S1 owns the only one); every non-fatal handler in the sales block now rolls the session back, so a failure can never cost the customer their reply (tested by forcing an exception in each step and a database error in the quote step); `offered_price` is bounded (<= 10bn), must be a figure in the customer's **current** message, and is dropped for a sold-out item; a pending offer on the lead (any turn) blocks the quote and code says a team member will confirm the price; cart refs resolve against what this session has seen (this turn's block, `offerings_shown`, items already wanted) and any unresolved line keeps the earlier rows, blocks the quote and is named by code; an offer **hands over for real** (`AUTO_ESCALATE`: ticket, `should_escalate`), with a separate `Price offer` owner alert keyed per lead, item and amount (uuid5, `entity_type="offering_offer"`, no CRM job) so a later offer is never swallowed by the once-per-lead cart alert; score rows are read from the stored items every turn; the old plan-tier quote never runs on a catalog cart; code says "noted your offer" only when a human picks it up, otherwise states the firm price; a row lock on the lead (`SELECT ... FOR UPDATE`, proven on Postgres) serialises parallel turns and quotes are idempotent per cart; Slack text is escaped (`& < >`); in-app, e-mail and CRM payloads carry items, listed prices, offered price and the currency symbol | Decisions taken by the lead (overflow without migration, auto-escalation on offers) and by me where marked ([call]: the per-conversation deep link was not built, the existing dashboard link is used) |
| Two score rows (`selected_items` 15, `price_offer` 5) appear **only when fired**; model-supplied `offered_price` can never fire the score key (its own name is `price_offer`) | `tests/sales/test_scoring.py` pins nine rows; existing leads keep nine |
| Lead `source` from the channel (`whatsapp`, `voice`, `hosted_page`, `chat_widget`) for every sales tenant | Spec 8.2; the old value was hard-coded |
| Test files live in `tests/offerings_ai/` | S1 owns `tests/offerings/`; separate directory avoids add/add conflicts |

## What's involved

New package `app/offerings/`: `grounding.py` (lookup, gate, fail-closed), `block.py` (render under the cap), `facts.py`, `rules.py`, `prompt.py` (channel formatting and the cart rules), `signals.py` (untrusted model output normalised), `guard.py` + `guard_flow.py` + `fallback.py` (**money path**), `cart.py` + `orchestrate.py` + `quote_text.py` (**money path**), `writer.py` (cards), `misses.py`, `turn.py` (what `chat.py` needs per turn). Pass 3 adds `tokens.py` (token parse, resolve, strip, price-order line), `offer_turn.py` (code-only bargaining replies) and the split of `guard.py` / `amounts.py`.

Changed shared code: `app/api/v1/endpoints/chat.py` (one block gated on `_offerings is not None`; lead orchestration, quote and `source` changes), `app/services/rag_service.py` (`catalog_addendum` kwarg: variant schema + system addendum; unchanged when absent), `app/sales/intent.py` (the variant schema).

**Outside the plan's file-ownership list (flagged to the lead):** `app/services/notification_service.py` (in-app text for `OFFERING_REQUEST`; CRM fan-out also for that event), `app/workers/sales_notifications.py` and `app/templates/emails/sales_rep_alert.html` (rep e-mail for `offering_request`), `app/sales/scoring.py` (fired-only catalog rows). Each is a small additive change.

`scripts/offerings_eval.py` (T7), `scripts/capture_offerings_ai.py` and `tests/fakes/live_stub_offerings.py` (T8), `docs/evals/offerings/2026-10-31-stand-in-model/` (output of the stand-in run).

## Verification

* **Unit and endpoint tests:** `tests/offerings_ai/` (**543 tests**): grounding and token cap, byte-identical prompt, schema variant and signal parsing, guard (**168 reply strings** in `test_guard.py`, **100 extraction strings** in `test_guard_extract.py`), false-block sets (`test_false_blocks.py`: fashion n40 and a 40-reply clinic/lawyer set, block rate ≤3%), offer turns (42), token flow (unknown/foreign token, resolution on every channel path, 14), guard flow and fallback, cards/memory/misses, cart/quote/offer/handover/alert/source/score (the row lock is proven on real Postgres in `test_lead_lock.py`), eval-harness self-tests. **Full unit suite on this head: 2,085 passed, 7 skipped** (the guard touches `chat.py`, shared code).
* **Findings that changed the code (each has a test that failed first):** (1) automated review: a concession at a price equal to another item's price slipped through; an echoed customer figure could be accepted in the same sentence; (2) the eval stand-in: a customer-named percentage could be accepted back; (3) the live capture: `cover_url` was the stored original, not the 400 px rendition; (4) the independent Opus review of the guard (relayed by the lead): (second Opus pass: naira written as `#`, two items swapping prices in one sentence, an unnamed sentence quoting any listed price, an echoed below-list figure stated as fact or agreed in pidgin/colloquial words, number-less agreement and discounts when the customer bargains, negation that does not govern the discount word, freebies and bundles, a customer figure above the list price stated as the price, an unbounded `offered_price`, a "noted your offer" with no handover) and the first pass: **stop-ship** `UnboundLocalError` on every "talk to a human" turn (offerings state not set on the auto-escalate path; fixed in `08c5c47` with 4 endpoint tests), "as you said" and other agreement forms, agreement in a separate sentence, adopted percentages, KB prices with agreement wording, glued/short/word-form amounts ("₦11,000only", "800", "fifteen hundred", "12 thousand five hundred"), number-less discounts, unnamed sentences using any listed price, false blocks on names/phones/dates/refs and `2,5k`; also a rejected reply's `offer_quote`/`offer_meeting` signals now never drive a quote, a guard exception takes the code fallback, and the per-turn gate got cheap.
* **Live run (2026-10-31):** real API + arq worker + Postgres 15 + Redis + fake sidecar, with the model replaced by a deterministic stand-in (`tests/fakes/live_stub_offerings.py`). 26 captures (re-run for the token regime: bargaining captures are now code-only replies, 25 shows a typed price regenerated into a token, 26 a guard fallback). **Proven live:** `meta.offerings` shapes, guard regeneration and fallback, offer storage and handover, cart to lead to quote, no second quote, `from` line without quote, notifications, support-mode isolation, WhatsApp text path and `source: whatsapp`. **Not proven live:** anything about the real model's wording, voice, strict mode, the real sidecar, SMTP.
* **Eval (T7):** 57 adversarial cases (including price-token cases: literal, foreign and mismatched tokens, `no_token_leak` check on every reply); the stand-in run passes 57 of 57 with guard interventions on the attack cases (`docs/evals/offerings/2026-10-31-stand-in-model/report.md`). That proves the harness and the guard, **not the model**. Two things only the real model can show, and the lead runs them on staging: `scripts/offerings_eval.py --model real` with 0 failed checks, **and** how often the real model writes the token correctly (every miss is a regeneration or fallback; target blocked or regenerated under 3 %).

## Operate / roll back

* Run the eval on staging (inside the API container, with its own `DATABASE_URL` and model key; it creates two scratch tenants and deletes them unless `--keep`): `python scripts/offerings_eval.py --model real --out /tmp/offerings-eval`. Read `report.md`; any failed check of rules 1-5 blocks the pilot.
* Pause the feature for one tenant: set `tenant_offerings_settings.enabled = false` (PATCH `/api/v1/offerings/settings`); the next turn is ungrounded and byte-identical to before.
* The guard's behaviour is visible per reply in `message.meta.offerings.guard`; audit with SQL over message meta for the first two weeks (spec 15 targets: blocked or regenerated under 3 %, fell back under 0.5 %).
* Revert: this branch adds no migration; reverting the merge removes the behaviour. Leads, interests, quotes and misses written meanwhile stay (they are ordinary rows).

## Follow-ups and known limits

* **Voice reads code lines only:** a token is never spoken and a negotiation on voice asks consent rather than handing over silently. TTS reading of `₦` amounts is still untested (spec 17.6).
* **Agreement with no number and no echoed figure** ("Okay." after a haggle) cannot be seen by the guard; rule 3, the eval and the pilot audit hold it. Availability wording is not machine-checked either (spec 17.1).
* **Flows are ungrounded in v1** (owner: no pilot uses a Flow with an AI node). `flow_engine.py` (AI node) and the automation replies in `chat_automation_orchestrator.py` call the model with no catalog block and no guard, so a tenant who adds an AI-node flow could have it quote a stale KB price for a catalog item. Add grounding there before any such tenant is onboarded (spec 7 risk list: record it there when the spec is next touched; not edited here).
* The guard compares numbers plus an explicit currency marker; a bare number cannot say which unit it is. Bare small numbers count as money only after a price cue ("costs 500"); a hand-written phone number with spaces may trigger a needless regeneration.
* Any percentage beside an item name is rejected, including "I can't offer a 20% discount on X": stricter than needed, costs one regeneration (the corrective line tells the model to say it without a number).
* A fallback lists the items that matched the question; with generic words it may list two similar items.
* **`render_quote_text` is wired nowhere in `app/`**: S4b T3 (WhatsApp second message) owns that wiring, it is not in S2. **Voice has no task:** a spoken reply says the model's text only, so a voice customer hears no quote; a known gap. S3/S4a render `meta.offerings` and `interests`.
* Parallel-turn safety is a row lock on the lead plus quote idempotency; a real concurrent chat run was not done.
* A guard-fallback offer to connect (`offer_escalation`) still waits for the customer's yes; a price offer hands over immediately.
* The not-found cue list is English plus a little pidgin; recall will be read from the miss log in the pilot.
